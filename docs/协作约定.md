# 协作约定

换对话、换人接手时先读这一份。项目本身的内容在另外三份文档里。

---

## 1. 这个项目是谁在做

- **作者不写代码。** 所有技术判断由我（AI）给出并说明理由，作者做决定和验收。
- 所以**解释要用大白话**，打比方，不堆术语。给了方案要说清代价，不能只说"建议这样"。
- 作者的判断很准：这一程里他两次直接说"不行，退回去"，都对——两次我都在往错的方向调。
  **他说不行就是不行，不要辩解，先撤回再重新想。**

## 2. 怎么干活

**一次一个任务，验证通过再提交，不要攒着一起做。** 这是作者明确提的要求，也被反复证明是对的：
几次难找的 bug 都是因为一批改动堆在一起，花了好几轮录屏逐帧才定位到。

每做完一步，报告三件事：

1. **改了哪些文件**（只列清单，不贴整段代码）
2. **每处改动在干什么**，大白话
3. **他本人怎么验证** —— 具体到"打开哪里、看到什么"或"敲哪条命令、出现什么算对"

**要作者在终端敲的命令，一律单独放进代码块，能直接复制粘贴。** 作者明确提的要求：

- 每条命令前写一句加粗的"这一步干什么"，命令后写一句"出现什么算对"
- 命令都从 `cd ~/CoinFlip &&` 开头，在哪个窗口里敲都能用
- **推到 GitHub 的命令也要给全**，不能只说"记得推送"
- 要在 Xcode 里点的操作写成"点哪里 → 再点哪里"，快捷键写明（如 `⌘R`）

所以：**凡是要编译或上真机的，都得他来跑，我只能给命令和"对的样子"。**

## 4. 定位问题的办法

**不要靠看代码猜性能问题。** 这一程里我连错三次判断，每次都是靠数据才找对：

- **录屏逐帧分析**最有效。要到一段录屏，用 ffmpeg 拆帧，算相邻帧的差异，
  差异接近 0 的就是卡住的帧。两次难找的卡顿都是这么定位的。
- **装探针量数据**，但注意两条教训：
  ① 要量**原始**帧间隔，推进动画用的那个 dt 夹过上限，会把卡顿抹掉；
  ② 探针频繁更新界面会**让尺子自己把要量的东西搞慢**，要改成事后报一次。
- **先做零改动的实验**（切 Release、按静音、重启手机），能排除一大半可能。

显示名 `Coin P`、搜索名 `抛硬币 P`、身份 `com.antheafsy.coinflip.polish`（`run.sh` 里同步改了一处）。

**合回 `main` 之前，先把这一次存档撤掉**（`git revert <那次存档的编号>`，
编号在 `git log` 里找标题含「Coin P」的那条），再合。

新功能建议开分支做，`main` 保持随时可上架：

```bash
git switch -c t25-edge-landing    # 开一条支线
git switch main                   # 切回主线
git switch -                      # 切回上一个分支
```
