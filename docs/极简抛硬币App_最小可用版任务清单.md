## 2. 实现过程中与原计划的偏差

记录在这里，是因为这些改动都有具体原因，以后回看才知道为什么这么做。

| 原计划 | 实际做法 | 原因 |
| --- | --- | --- |
| 硬币悬空正对镜头 | 躺在看不见的水平面上，镜头斜上方看 | 对照参考视频，"落在平面上"才有真实感 |
| 落地后弹三下 | 边缘先着地 → 打转摇摆 → 躺平，共 11 次磕碰 | 实测参考录音，真硬币几乎不弹，主要是边缘磕碰 |
| 镜头固定 | 落定后绕到上方并推近成特写 | 参考视频的分镜，也是"揭晓结果"的仪式感来源 |
| 等待时硬币悬浮呼吸 | 硬币静卧，改由镜头缓慢游移 | 硬币躺在平面上还浮起来，自相矛盾 |
| 只有落地一声 | 抛起 + 落地 + 一串磕碰 | 参考录音里抛起也有声音，且余韵很长 |
| 单一贴图 | 贴图 + 法线贴图 + 环境贴图 | 没有法线图，浮雕像印花；没有环境反射，金属发灰 |
| 弹性 0.2 | 0.055 | 真硬币落在硬平面上几乎不弹 |

## 2.5 已知问题

| 问题 | 情况 | 为什么还没修 |
| --- | --- | --- |
| **抛掷时偶尔掉帧** | 约每 10 次有 1 次，画面冻住约 0.1 秒，出现在**抛掷开始后 0.23 秒**；平时最慢的一帧也有 20–30ms，卡的那次 70–133ms | **已排除**：脱手那一刻的处理全部 0–2ms（存档、排时间表、排声音与震动都不是瓶颈）；把震动搭表挪到后台**反而更糟**，已撤回。卡住的时刻代码里没有任何事件。**最大嫌疑是跑的是开发版**——Swift 开发版不做优化编译，每帧的三角函数、幂、四元数可能慢 5–10 倍。下次从三个不用改代码的实验开始，见下方 |
| **长时间开着会微微发烫** | 开着十分钟后手机背面中心偏上略温 | **决定不做，优先保手感。** 只要 App 开着就一直满帧渲染（等待时镜头在缓慢游移）。真正的降帧要让系统少刷新屏幕，而**停下来的东西重新动起来是要花时间的**，手指碰上去那一下很可能落在一个刚唤醒的慢帧上——正好撞在起手的手感上，而这类改动今晚已经栽过两次。技术上 RealityView 也没有公开接口能调刷新率，绕路的办法（减灯、关环境反射、降分辨率）都会直接伤到金属质感。而且这个 App 是"掏出来抛一下收起来"，十分钟持续开着不是真实场景。**零风险的半步**（没做）：三十秒没人碰就停掉镜头游移，手指一碰立刻恢复——不动渲染机制所以不影响触摸响应，省的是 CPU 那部分，代价是静置久了画面完全不动 |
| **硬币偶尔有横切的灰边** | 飞过低空、同时侧着的时候，地面那张半透明平面挡在镜头和下半边硬币之间。低抛时更容易看到 | 根因是**我们在渲染一件物理上不可能的事**：硬币半径 0.33，而轻抛只有 0.10——一枚半径 0.33 的硬币要翻身，侧过来那一刻圆心必须离地 0.33 以上。试过两条路都被真机否掉：地面下沉 0.26 会让阴影明显脱开；中间挖洞会把阴影变成环、且放大后掉帧拖垮手感。真要根治得抬高最低抛掷高度，那会动到已经认可的手感，**留到 T23 调手感时一起定** |

**2026-10-12 更新（P08）**：在 polish 分支（已有银河背景、星点、承托光、背景弹簧跟随）用**开发版**抛 15 次，**卡了 3 次，都在上抛过程中**。
随后正式版（Release）15 次**卡 2 次，同样在上抛阶段**。所以**不是开发版的锅**，用户手里的版本一样会卡。
和最小可用版时（开发版约 1/10）相比可能略多，但这次背景加了不少东西，不能直接比。

### 掉帧问题：下次从这三个实验开始（都不用改代码）

1. **切到正式版跑一次**（最关键）。Xcode → Product → Scheme → Edit Scheme →
   Run → Build Configuration 改成 Release → `⌘R`，抛 15 次凭感觉判断。
   不卡了就说明是开发版的锅，用户拿到的正式版没这问题，不用改任何东西。
   测完改回 Debug。
2. **按静音键抛 15 次**。明显减少就说明是音频那条路。
3. **重启手机后立刻测**。排除后台有别的 App 在抢资源。

排查时可以临时装一个掉帧探针（曾经写过，在 git 历史里找 FrameMonitor）。
两个教训记下来：① 要量**原始**帧间隔，推进动画用的那个 dt 夹过上限，
会把卡顿抹掉；② 探针每秒往外写四次会让底部那行字反复重算，
**尺子自己把要量的东西搞慢了**，必须改成抛掷结束后才报一次。

---

灰边的两个较轻的缓解手段，没做，想要随时说：
- 把地面的透明度整体调低（`make_assets.py` 里 `ground_fade` 的 `peak`，0.95 → 0.45 左右）。灰边的对比度跟着减半，光晕只是淡一些，不动几何、不影响帧率。
- 把 `minHeight` 从 0.12 抬到 0.2 左右。不能根治，但能明显减少轻抛时撞上的时长。

## 5. T25 边缘立币（第三种答案）

**依赖**：T24 必须先完成。

**为什么要等**：这是一个新功能，而且会动到"结果"这条贯穿全身的主线。
主线还没验收完就动它，出了问题会分不清是新功能带来的，还是原来就有的。
先给"这个版本是对的"打一个桩，再开工。

### 要做的是什么

极低概率下，硬币落地弹几下之后**竖立在边缘上**，不给日也不给月。
震动与平常完全不同，屏幕中央浮现一道极细的高光。
它不只是彩蛋，是打破二选一的"第三种答案"。

### 开工前必须先定的三件事

| 要决定的 | 两条路 | 备注 |
| --- | --- | --- |
| **概率** | 1/1000 当传说 / 1/200 当彩蛋 | 一个人一辈子大概抛两三百次。1/1000 等于绝大多数人永远见不到，而且真撞上的人第一反应多半是"卡 bug 了"。倾向 1/200 |
| **立住之后呢** | 只是"这次没结果，再抛" / 就这么立着，什么都不说 | 后者才是"第三种答案"。要一并想清楚：冷启动读到上次是立币，应该还立在那儿 |
| **要不要写明概率变化** | — | 加了之后日月各是 49.95%，不再是严格五五开。实际无所谓，但本项目一直是"结果先定、动画只负责演"，这条性质该在技术文档里写明，不能悄悄改掉 |

### 难在哪、不难在哪

**几乎免费**（现有机制直接能用）：

- **立币的姿态** —— 现在的落地流程是「边缘先着地 → 歪着打转 → 收平躺下」，
  立币就是**不要最后那一步收平**。翻转角度从"若干个半圈"改成
  "若干个半圈再加四分之一圈"，硬币自然停在竖着的位置。摇摆那套递减原样能用。
- **震动** —— 精细震动引擎正好擅长这个。换一张震动表即可：
  一串越来越快越来越轻的脆响（在边上来回晃），最后一记沉的定住。
- **概率** —— 决定结果的地方只有一行。

**要花力气**：

- **镜头** —— 现在的特写从正上方 78 度俯看，立着的硬币从上面看就是一条线。
  立币要配一套自己的分镜：压到很低的角度平视过去。
- **阴影** —— 躺着投圆影，立着投细长条。现在的阴影是等比缩放的圆片，
  要支持两个方向分别缩放。
- **那道高光** —— 全新的东西，不是任何现有参数的调整，要反复试几轮。
- **减少动态效果模式** —— 也得想好立币在简化动画下怎么呈现。

### ★ 真正会咬人的一处 ★

「结果」这个类型从头到尾只有两个值：日、月。它串在存档、状态机、
半圈数奇偶修正、静置姿态，以及一组专门反向验证
"演完之后朝上的面必须等于当初决定的结果"的测试里。

加第三种结果，等于把这条贯穿全身的线换掉。改动本身不难，**难在容易漏**。
漏一处的后果不是崩溃，是"偶尔结果不对"——在抛硬币 App 里这是致命的，还极难复现。

**所以第一个子任务必须是：把结果类型和那组一致性测试改成三值，让测试先红。**
红了之后再去改代码，漏哪儿它会立刻告诉你。这组测试已经抓到过两次实现上的错。

### 拆解（开工时再细化）

1. 结果类型改为三值，一致性测试同步改三值 —— **先让测试红**
2. 存档与冷启动支持第三种结果
3. 时间表支持"停在竖立"：四分之一圈收尾 + 专属的弹跳与摇摆
4. 立币专属镜头
5. 阴影支持非等比缩放
6. 立币专属震动与声音
7. 中央那道极细的高光
8. 概率接进随机器，并补一个"大量抛掷后三种结果占比符合设定"的测试

### 验收标准

- [ ] 把概率临时调成 1/2，连抛十次，立币的姿态、镜头、阴影、震动、高光都对
- [ ] 概率调回正式值后，一致性测试全部通过（含三值反向验证）
- [ ] 立币之后切后台再回来，不会变成日或月
- [ ] 立币之后冷启动，硬币仍然立着
- [ ] 开启"减少动态效果"后，立币仍能正常呈现

- 线索（未验证，只是时间对得上）：卡的时刻约在脱手后 0.23 秒，抛起时镜头从特写快退回远景正好用 0.22 秒

### 翻转方向跟手指（P09 遗留，以后优化）

现状：代码在、功能开着，正上方划没问题，斜着划角度和手指对不上。已经做过的三版：

1. 第一版：手指角度直接照搬到地面——划 45° 屏幕上像 65°；且"往哪边翻"没放进中转盒子（CoinSceneState），每帧读到的永远是 0，作者看着"没有任何变化"
2. 第二版：先把镜头斜看的透视折算掉（`axisYaw(forFlipDirection:)`，压扁系数 sin 28°）；进动/章动/打转跟着左右镜像（`FlipAnimator.turnSide`）；翻滚改为往屏幕里翻（`tumbleSign = -1`）
3. 第三版（**作者还没真机验收**）：拖动时"跟手原地转"按手指方向加权（`spinFollowWeight`，离竖直 50° 内不转、65° 外全跟），不再和横拨打架；手指往上提时朝手指方向掀起

**下次接着查的头号嫌疑**（还没验证）：进动在飞行中把翻转轴转了 60°。
往右上划时它朝哪边转是由 `turnSide` 定的——它会把轴往回带过中线，飞到半空时看到的翻转方向已经不是手指方向了。
可以试：斜着划时把进动调小、或改成朝外转，看角度是否就对上。
其他可能：抛起那一下镜头正从特写（78°）退回远景（28°），透视折算按 28° 算，起手那几帧不准。
问作者时可以问："往右上划，硬币看起来更偏右，还是更偏上？"

停稳不扭、结果正确这两条，FlipDirectionTests 已经用四元数逐一核对过（所有方向、2~8 个半圈）。

### B 硬币倒影（2026-10-12 讨论过，作者决定先做 A，P08 之后提醒）

做法：硬币底下多一枚倒过来的硬币，透过看不见的玻璃淡淡映在星空上。远景和飞行中最明显，特写基本被硬币挡住。

- **好处**：承托感最强（比影子还强）；把硬币和背景连成一体；飞行时硬币往上、倒影往下，最接近参考视频
- **难点 ①（最要紧）会提前泄露结果**：倒影映出朝下那面。落地斜 42°、等镜头推近才揭晓的"那一口气"会被倒影剧透。
  办法：倒影用一套**模糊、低对比的币面贴图**，只看得出是银币、认不出图案
- **难点 ② 硬币会穿进自己的倒影**：§2.5 那个老问题（轻抛 0.10 高、半径 0.33，翻身时下缘必然沉到地面以下）。
  办法：贴地且侧着时让倒影淡出（同影子的处理）；或抬高最低抛掷高度（会动手感）
- **代价**：每帧多画一枚硬币（硬币是画面里最贵的东西），所以要先有 P08 的帧率基准；倒影亮度要真机来回调（真实约实物的一到两成）
- **工作量**：约 A 的三四倍，分四步：倒影本身 → 模糊贴图 → 穿插处理 → 亮度调校
- A 的承托光可以留着当倒影底下那层"玻璃"，不白做

### 每项的要点（开工时看）

- **P01、P04**：只改 `make_assets.py` 生成图片那一步，写进 PNG 前掺入肉眼看不见的细噪点。运行时开销不变。
  已量过的原因：背景微光 `ground_fade` 的 `peak=0.313`，透明度最高只有 80 级，约每 6 px 跳一级；
  浮雕坡度缓，法线压到 8 位后只剩几个方向，光一动就像等高线。
  P04 排在 P05 之前，是因为呼吸要让高光在币面上流动，正是最暴露台阶的场景。噪点别多到在特写里显出颗粒。
- **P02**：已完成，见上方"P02 记录"。
- **P03**：P02 删掉白色光晕后，作者反馈"影子几乎不可见、硬币和背景脱节"，P03 改为先解决承托（方案 A）。
  原定的"影子档位 48 → 更多"：承托光很暗，48 档里相邻两档在屏幕上差不到 1 级亮度，看不出跳，**先不做**，真机上看到跳再加。
  立币分支第 5 步改的是"立着时影子变细长条"，和这里不冲突。
- **P05**：**开工前先和作者重定"呼吸"**——原定的呼吸 B（背景微光一明一暗）用的光晕已在 P02 删掉。
  候选：只留 A（币面高光流动）；或改成银河本身极缓慢地明暗起伏。
  **硬币本身不能浮起来**，躺在平面上还浮动是自相矛盾的，当初就是因此改成镜头游移。
  呼吸只靠光（高光流动 + 微光明暗），镜头游移保留。减少动态效果下全部关掉。
- **P06**：远景就是现在抛掷时用的那个镜头（离地 28°），不用新建。碰屏幕、横拨、双指缩放都算"有操作"，计时重来。
  推远后恢复镜头游移。减少动态效果下不自动推远。
- **P07**：两根手指不会同时落下。**第二根手指一落下，第一根手指的提起就作废，硬币落回原处。**
  跟手缩放，松手吸到最近一档，吸附时轻震（同横拨自转那种"嗒"）。减少动态效果下保留，因为是用户自己动的手。
- **P08**：做法见 §2.5 "掉帧问题"的第 1 个实验。
- **P09–P11**：**只改"怎么转"，不改"转几个半圈"。** 正确性靠半圈数的奇偶，任何新加的转动都必须转回整圈或绕竖直轴。
  已经为这件事付过一次学费：收尾摆动曾是 1.2 圈，作者当场看出"落地看到的面和结果接不上"。
  **时长不能变长**：好用就在于快，"丰富"要做成每次不一样，不是每次更长。
- **P12、P13**：读手机动作感应器（不弹授权窗）。只对"变化"做反应，人拿手机本来就歪着；只在静止时生效。
  **最难的一处**：晃得偏离中心时手指一划，起飞要从当前位置平滑接过去，不能瞬移。
  感应器数据来自另一条线程，接进来要谨慎（以前把震动挪到后台反而更卡）。主要在远景里生效，特写里一滑就出画。
  模拟器没法摇，全靠真机验，来回轮数会最多。
